# Backend-backed treatment-plan workflows

This change replaces the fabricated frontend treatment domain with explicit adapters for `/api/v1/treatment`, real patient/provider UUIDs, backend statuses, actual procedure routes, and backend-owned totals. Procedure creation now builds the model from validated `TreatmentProcedureCreate` fields, removing the attribute-name crash while retaining tenant checks on linked records. The UI no longer invents clinicians or simulates insurance coverage. **Confirmed:** the integration still hides valid records, exposes actions to roles the API rejects, and adds test files despite the task constraint.

Watch for: **confirmed** plans older than 90 days or beyond the first 50 are invisible; **confirmed** patients beyond the first 100 cannot be selected; **confirmed** admin and dentist controls invoke routes their roles cannot use; **confirmed** two untracked test files violate the no-new-test-files requirement.

**Verdict**: NEEDS_CHANGES

## High-level view

The backend and frontend now share one vocabulary. `plan_name`, costs, dates, procedure fields, and envelopes are adapted once in `treatmentPlanApi`; the UI uses camel-case domain types and reloads backend totals after procedure mutations.

Procedure creation follows the schema rather than nonexistent aliases. Optional appointment and pre-authorization references are bound to the plan’s practice and patient before persistence.

**Confirmed:** the page treats a bounded response as the complete treatment record. The backend applies a 90-day window and 50-row limit, while the create dialog exposes only the first 100 active patients.

**Confirmed:** owners, admins, and dentists can open the page, but mutation permissions split those roles differently. With no action-level gating, admins and dentists receive controls that return 403.

Focused backend assertions, type checking, and the existing page Vitest pass. **Confirmed:** adapter coverage sits in two new untracked test files rather than existing focused suites, and pagination and role boundaries remain untested.

## Bounded treatment data is presented as complete

**Confirmed:** `TreatmentService.list_treatment_plans_page` defaults to `limit=50` and `default_days=90` (`coredent-api/app/services/treatment_service.py:218-267`). `treatmentPlanApi.getPlans` sends no range or page and discards `total` and `next_offset` (`coredent-style-main/src/services/treatmentPlanApi.ts:224-230`). Active plans can disappear solely because of age, and every matching row after 50 is omitted without indication. Add an explicit date policy and pagination/infinite loading, or return the complete collection this page assumes.

**Confirmed:** name hydration and `TreatmentPlanDialog` both request `patientsApi.list({ status: 'active', limit: 100 })` and consume only that page (`coredent-style-main/src/pages/TreatmentPlans.tsx:58-71`, `coredent-style-main/src/components/treatment/TreatmentPlanDialog.tsx:59-70`). Later patients cannot receive a new plan, and their existing cards show “Name unavailable.” Use a server-backed patient typeahead or paginated selector.

Not tested: a plan outside 90 days, a second treatment-plan page, or an active patient beyond the first patient page.

## Treatment controls disagree with backend authorization

Optional procedure references are now checked against the plan’s tenant and patient. **Confirmed:** the UI authorization around those writes is inconsistent: `/treatment-plans` admits owner, admin, and dentist users (`coredent-style-main/src/routes/config.tsx:132-142`), create/update/add/complete require owner or dentist, and plan/procedure deletion requires owner or admin (`coredent-api/app/api/v1/endpoints/treatment.py:201-205,288-292,326-330,506-510,564-568,619-623`). The page renders New Plan, Designer, completion, cancellation, and deletion without role checks (`coredent-style-main/src/pages/TreatmentPlans.tsx:219-263,301-303`; `TreatmentPlanDetails.tsx:237-242`). Align backend policy or hide/disable each disallowed action with an honest read-only state.

Not tested: admin or dentist behavior for cancellation, procedure deletion, creation, editing, or completion.

## Contract tests were added outside the allowed file set

**Confirmed:** `coredent-style-main/src/services/__tests__/treatmentPlanApi.test.ts` and `coredent-style-main/src/components/treatment/__tests__/TreatmentPlanCard.test.tsx` are new untracked files. Move their wire-adapter and display assertions into existing tracked focused suites, then remove the new files. The tracked page suite covers UUID creation, backend statuses, actual procedure methods, and loading failure, but mocks the adapter and does not cover the two integration boundaries above.
